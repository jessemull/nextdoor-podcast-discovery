# Supabase migrations

Two Supabase projects are used: one for development (Preview / local) and one for production. Apply the same schema to both. See [ENVIRONMENTS.md](ENVIRONMENTS.md) for which project each environment uses.

## New project (e.g. production, no schema yet)

1. Open the Supabase project in the Dashboard → SQL Editor.
2. Run `database/bootstrap.sql` once. Paste the file contents and execute.
3. Optionally run `database/seeds/seed_neighborhoods.sql` for seed data (e.g. dev only).

`database/bootstrap.sql` is the concatenation of all files in `database/migrations/` in numeric order. It is generated by `make db-bootstrap`. Do not edit it by hand. After adding a new migration, run `make db-bootstrap` and commit the updated bootstrap so new projects get the latest schema.

**Do not run bootstrap on a project that already has these tables.** It uses plain `CREATE TABLE` (no `IF NOT EXISTS`) and will error with "relation … already exists".

### Full schema reset (wipe and re-bootstrap)

If you need to reset an existing project to a clean schema (e.g. wipe prod and reapply from scratch):

1. In Supabase SQL Editor, run `database/scripts/drop_all_tables.sql`. This drops all application tables and the `update_updated_at_column` function.
2. Run `database/bootstrap.sql` once.
3. Optionally run `database/scripts/truncate_all_data.sql`’s (Default neighborhood, default weight config, and settings) so the app and scraper work.

All data in the dropped tables is permanently removed.

## Existing project (schema already applied)

Run only **new** migration files—those not yet applied—in numeric order from `database/migrations/`. Copy each file’s contents into the SQL Editor and execute. Repeat for the other project (dev and prod) so both stay in sync.

### Reload API schema cache after migrations

The Supabase API (PostgREST) caches the database schema. After running migrations or bootstrap in the SQL Editor, the API may still return "Could not find the function … in the schema cache" until the cache is refreshed. In the same project's SQL Editor, run:

```sql
NOTIFY pgrst, 'reload schema';
```

Then retry the request. No rows are returned; the notification tells PostgREST to reload tables and RPCs.

### Repair feed RPCs (function missing in production)

If the API still reports that `get_posts_with_scores` (or `get_posts_with_scores_count`) is not in the schema cache after a reload—for example after a partial reset or failed bootstrap—run `database/scripts/repair_feed_rpcs.sql` in the project's SQL Editor. It recreates both functions and triggers a schema reload. Then retry the app.

## Adding a new migration

1. Add a new file to `database/migrations/` with the next number and a descriptive name (e.g. `044_new_feature.sql`).
2. Run the new migration against existing dev and prod projects (SQL Editor).
3. Run `make db-bootstrap` and commit the updated `database/bootstrap.sql` so future new projects include the change.
